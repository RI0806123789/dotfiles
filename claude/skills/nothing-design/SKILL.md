# Nothingに触発された UI/UX デザインシステム

スイスタイポグラフィ、工業デザイン（Braun、Teenage Engineering）、および現代のインターフェース設計で鍛えられたシニアプロダクトデザイナーのツールキットです。単色を基調にし、タイポグラフィを中心に情報密度は高いが雑然としません。ダークモードとライトモードは同等の配慮で設計します。

**デザイン作業を始める前に、どのGoogleフォントが必要で、どう読み込むかを宣言してください**（`references/tokens.md` のセクション1を参照）。フォントが既に利用可能だと仮定してはいけません。

---

## 1. デザイン哲学

- **削ること（AddではなくSubtract）**：すべての要素はそのピクセルに値しなければなりません。デフォルトは削除です。
- **構造が装飾である**：グリッド、データ、階層そのものを見せます。
- **単色をキャンバスとする**：色はイベントでありデフォルトではありません — ただしデータ状態の符号化時は例外です（セクション3参照）。
- **タイポグラフィが主役**：サイズ、ウェイト、スペーシングで階層を作ります — 色やアイコン、境界線ではありません。
- **両方のモードを同格に扱う**：ダークモードはOLEDブラック、ライトモードは温かいオフホワイト。どちらも「派生」扱いにせず同等の配慮を与えてください。どちらのモードで始めるかユーザーに確認してください。
- **工業的な温かさ**：技術的で精緻だが冷たくないこと。人の手の温もりを感じさせます。

## 2. 作法 — 構成ルール

### 2.1 ビジュアル階層：三層ルール

各画面には正確に**三つの重要度レイヤー**が存在します。二つでも五つでもありません。三つです。

| 層 | 何 | 方法 |
|-----|----|------|
| **プライマリ** | ユーザーが最初に見る“ただ一つ”のもの。数値、見出し、状態など。 | Doto または Space Grotesk をディスプレイサイズで。 `--text-display`。48–96px の余白を確保。 |
| **セカンダリ** | 補助的な文脈。ラベル、説明、関連データ。 | Space Grotesk を本文／サブヘッディングで。 `--text-primary`。プライマリに対して 8–16px で近接させてグループ化。 |
| **ターシャリ** | メタデータ、ナビゲーション、システム情報。目には見えるが競合しない。 | Space Mono をキャプション／ラベルで。 `--text-secondary` または `--text-disabled`。全て大文字。端や下部に寄せる。 |

**テスト方法:** 画面を細めて見てください。何が最も重要か判別できますか？二つが競合しているなら、どちらかを縮小、フェード、または移動させる必要があります。

**よくある誤り:** すべてを「セカンダリ」にしてしまうこと。均等なサイズと均等なスペースは視覚的に平坦です。大胆になってください — プライマリはとてつもなく大きく、ターシャリは極端に小さくする。差が階層を生みます。

### 2.2 フォントの規律

画面ごとに最大で使用するのは：
- **2つのフォントファミリー**（Space Grotesk + Space Mono。Doto はヒーロー時のみ）
- **3つのフォントサイズ**（大・中・小）
- **2つのフォントウェイト**（Regular + もう一つ — 通常は Light か Medium、Bold は稀）

これを予算だと考えてください。追加のサイズやウェイトは視覚的一貫性のコストになります。新しいサイズを導入する前に、その差をスペーシングや色で表現できないか検討してください。

| 判断 | サイズ | ウェイト | 色 |
|------|:------:|:--------:|:--:|
| 見出し vs 本文 | Yes | No | No |
| ラベル vs 値 | No | No | Yes |
| アクティブ vs 非アクティブ ナビ | No | No | Yes |
| ヒーロー数値 vs 単位 | Yes | No | No |
| セクションタイトル vs 内容 | Yes | Optional | No |

**経験則:** 新しいフォントサイズに頼りたくなったら、まずはスペース（余白）を調整してください。

### 2.3 スペーシングを意味として扱う

スペーシングは関係性を伝える主な手段です。

```
タイト (4–8px)   = "これらは一緒に属する" (アイコン + ラベル、数値 + 単位)
ミディアム (16px) = "同じグループ内の別アイテム" (リスト項目、フォームフィールド)
ワイド (32–48px)  = "ここから新しいグループが始まる" (セクション区切り)
ヴァスト (64–96px) = "これは新しいコンテキスト" (ヒーロー→コンテンツ、大きな区分)
```

**もし区切り線が必要なら、多くの場合スペーシングが間違っています。** 区切り線はスペーシングコントラスト不足の症状です。構造が同一のデータ密なリストでのみ使用してください。

### 2.4 コンテナ戦略（上から優先）

1. **まずはスペースで表現する**（近接でグループ化）
2. 単一の区切り線
3. さりげないボーダーアウトライン
4. 背景の変化を伴うサーフェスカード

各ステップは視覚的重みを追加します。最も軽い手段で済ませてください。最も重要な要素をボックスで囲まないでください — 背景に浮かせて見せます。

### 2.5 色を階層として使う

単色システムでは、グレースケール自体が階層です。画面ごとに最大4レベルまで：

```
--text-display (100%) → ヒーロー数値。画面につき一つ。
--text-primary (90%)  → 本文、主要コンテンツ。
--text-secondary (60%) → ラベル、キャプション、メタデータ。
--text-disabled (40%) → 無効状態、タイムスタンプ、ヒント。
```

**赤 (#D71921) は階層の一部ではありません。** それは割り込みです — 「ここを今見て」。緊急なものがない限り画面に赤は置かないでください。

**データ状態色**（成功=緑、警告=アンバー、強調=赤）は「アクセントは1つ」ルールの例外です。データ値自体に色を適用し、ラベルや行の背景には適用しないでください。フルカラーシステムは `references/tokens.md` を参照してください。

### 2.6 一貫性 vs 変化

**一貫して守ること：** フォントファミリー、ラベルの扱い（常に Space Mono を全大文字で）、スペーシングのリズム、色の役割、コンポーネントの形状、配置。

**画面ごとに正確に1箇所だけパターンを破ること：** 大きすぎる数値、四角だらけに対する円形ウィジェット、灰色の中の赤いアクセント、Doto のヘッドライン、他がタイトな中での大きな余白。

この一箇所の破りがデザインです。無ければ無味乾燥、二つ以上あれば混乱します。

### 2.7 構成のバランス

**非対称 > 対称。** 中央寄せは陳腐に感じます。意図的にアンバランスな構成を好みます：
- **左は大きく、右は小さい：** ヒーローメトリクス + メタデータのスタック。
- **上寄せ重め：** 上部に大きな見出し、下部はすっきり。
- **エッジに固定：** 重要要素は画面端にピン留め、ネガティブスペースは中央に。

重たい要素はさらに重たい要素で釣り合せるのではなく、空きで釣り合いを取ります。

### 2.8 Nothingらしさ（The Nothing Vibe）

1. **余白による自信**：広い余地を残す。無駄に埋めない。
2. **小さなディテールの精度**：文字間、正確な灰色、4px 間隔。マイクロな意思決定が仕上がりを左右する。
3. **データそのものが美**：`36GB/s` を Space Mono で 48px 表示することが視覚そのもの。イラストは不要。
4. **機械的な誠実さ**：コントロールはコントロールらしく見える。トグルは物理的なスイッチ、ゲージは計器。
5. **驚きの一瞬**：ドットマトリクス見出し、円形ウィジェット、赤いドットなど。抑制があるからこそその一瞬が効く。
6. **打楽器的で滑らかでない**：UIサウンドはスウィッシュではなくクリック、ティック。トランジションは機械的で正確な感触。

### 2.9 データ密度の高い画面での表現の多様性

3つ以上のデータセクションが同一画面に現れる場合、表現形式を変えて視覚的な違いを出します：

| 形式 | 適用先 | 重み |
|------|--------|------|
| ヒーロー数値（大きな Doto/Space Mono） | 単一の主要指標 | 重 — 1回だけ使用 |
| セグメント化プログレスバー | 目標への進捗 | 中 |
| 同心円／アーク | 複数の関連パーセンテージ | 中 |
| インラインコンパクトバー | 行内の副次メトリクス | 軽 |
| 値のみ（ステータス色付き） | 比率を示さない値 | 最軽量 |
| スパークライン | 時系列の傾向 | 中 |
| スタット行（ラベル + 値） | 単純なデータポイント | 軽 |

主セクション → 最も重い扱い。二次は異なる形式で。三次は最軽量で表現します。形式を変えながら声（トーン）は揃えること。

## 3. アンチパターン — 絶対にやってはいけないこと

- UIのクロームにグラデーションを使わない
- シャドウやブラーは使わない。フラットな表面とボーダーで分離する。
- スケルトンローディングを使わない。`[LOADING...]` テキストやセグメント化スピナーを使用する。
- トーストポップアップを使わない。インラインのステータステキストを使う：`[SAVED]`, `[ERROR: ...]`
- 哀しげな顔のイラストやキャラクター、多段の空状態テキストを使わない
- テーブルのゼブラストライプは禁止
- 塗りつぶしアイコン、多色アイコン、UIに絵文字を使わない
- パララックス、スクロールジャック、意図しないアニメーションは禁止
- スプリング／バウンス系のイージングは禁止。微かなイーズアウトのみ使用。
- カードのボーダー半径は16pxを超えない。ボタンはピル（999px）かテクニカル（4–8px）にする。
- データ可視化：色を導入する前に **不透明度**（100%/60%/30%）や **パターン**（実線/ストライプ/ドット）で差をつける。

## 4. ワークフロー

1. **フォントを宣言する** — どの Google Fonts を読み込むかユーザーに伝える（`references/tokens.md` を参照）
2. **モードを確認する** — ダークかライトか。どちらもデフォルトではない。
3. **階層をスケッチする** — コードを書く前に三層を特定する。
4. **構成する** — 作法（セクション 2.1–2.9）を適用する。
5. **トークンを確認する** — 正確な値は `references/tokens.md` を参照する。
6. **コンポーネントを構築する** — パターンは `references/components.md` を参照。
7. **プラットフォームに適合させる** — 出力先に合わせて `references/platform-mapping.md` を参照。
